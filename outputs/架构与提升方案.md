### 1.3 AI 引擎的决策管线（当前实现的全貌）

`getBestMove(level, forColor)`（行 3188）是一条**硬编码的优先级阶梯**，而不是一个统一搜索：

```
① findImmediateWin(me)            一步成五 → 直接下
② findImmediateWin(opp)           对方一步成五 → 必挡
③ findVcfWin(me, 10层)            能连续冲四杀 → 下
④ findVcfWin(opp, 10层)           对方能连续冲四杀 → 堵
⑤ findDoubleThreat(me)            一手双四/活四 → 下
⑥ resolveThreats(me, opp, true, false)   己方活四 / 挡对方活四
⑦ findDoubleKill(me)              一手双三/三四 → 下
⑧ findVctWin(me, 10层)            能连续活三杀 → 下
⑨ findVctWin(opp) → vctDefense    对方能连续活三杀 → 堵
⑩ findOpponentDoubleThreat(opp)   对方下一步成双三 → 抢先占
⑪ resolveThreats(me, opp, false, false)  己方活三进攻
⑫ bookMove(level, me)             开局库（仅盘面 ≤8 子）
⑬ openingMove(level)              规则式开局
⑭ bestBySearch(hard) / bestBySearch(medium, 400ms) / bestByScore(easy)
```

底层零件：`lineInfo`（数连子+开放端+可达性）→ `lineScore` 查 `PATTERN_TABLE` → `threatLevel` / `countThreats` / `evaluateCell` / `scoreFor`；`evaluateBoard` = 双方棋型分差 + 连接性 + 中心权重 + `comboBonus` + `threatSpaceBonus`；`minimax` 带 Zobrist 置换表 + 历史启发 + 杀手表 + 强制走法收窄；`bestBySearch` 迭代加深 3→5→6 层，单步预算 2500ms。

### 1.4 服务端

原生 Node，手写 WebSocket 帧解析、5 位房间号、服务端权威判胜/换手/坐标校验、猜先（服务器掷币）、token 重连快照、心跳 15s/45s 判死、房间 15 分钟回收、20 msg/s 限频。**这一块质量明显高于前端**：协议文档完整、状态机清晰、异常分支齐全、还有 87 项协议断言测试（`work/ws-test.js`）+ 56 项浏览器端到端测试（`work/online-e2e.js`）。

## 二、实测证据：AI 强度到底卡在哪

我写了 4 个探针脚本（都在 `work/`，见附录），跑了这些实验：

### 证据 1：**加倍时间/深度/宽度，棋力一点都不变**

同一对局条件下让"参数增强版" vs "原版"各跑 6 局（交替执黑）：

| 实验 | 改动 | 结果 |
| --- | --- | --- |
| VCF 加深 | 10 层/5000 节点/250ms → **20 层/20000 节点/800ms** | A 胜 3 / B 胜 3，**平均总手数 31** |
| 搜索加宽 | 2.5s/16 候选 → **10s/24 候选/30 根候选** | A 胜 3 / B 胜 3，**平均总手数 31** |
| VCT 加宽 | 10 层/5000/300ms → **16 层/20000/1200ms** | A 胜 3 / B 胜 3，**平均总手数 31** |
| 预算翻倍 | 2500ms → **6000ms** | 高预算 4 / 标准 4，**8 局全部 31 手、全部黑胜** |

**结论：把搜索预算翻 2.4 倍、VCF 窗口翻倍、候选宽度 +50%，胜率一分未得，每局手数一字不差。** 说明这些参数**目前根本没进到决策的关键路径上**——`SEARCH_BUDGET_MS`/`VCF_*`/`CANDIDATE_LIMIT` 这些"AI 强度旋钮"调了等于没调。

### 证据 2：**90% 的着法根本没进搜索，是硬编码阶梯直接拍的**

在 19 路 AI 自对局里插桩 `bestBySearch` 的调用与到达层数（`work/_probe-depth.js`）：

```
手数 轮到 耗时ms  实际情况
  10   黑   157   d3: 47ms / 18 根候选     ← 唯一一次真正搜索
  11   白   137   战术层直接落子（未进搜索）
  12   黑     1   战术层直接落子
  ...
  22   黑   214   （进了搜索，但超预算没完成任何一层）
  26   黑     3   战术层直接落子
  ...
→ 黑胜，共 31 手
```

一整局 ≈30 手，**只有 1~3 手真正跑过搜索**，其余全靠 ②~⑪ 的固定阶梯。而实测 `hard` 档几乎从不吃满 2500ms 预算（平均 130ms，最大 611ms）——"困难档思考 2.5 秒"只发生在极少数一直没分出胜负的残局（perf 测试里第 50 手出现过 2.7s）。

### 证据 3：**先手必胜在引擎内部成立**

上面 8 局全部是"执黑方获胜、31 手结束、无变化"。也就是说：**当前引擎作为白方无法防住自己的黑方**，而且每局走法几乎完全相同（随机扰动被阶梯绕过了）。

### 证据 4：瓶颈在评估，不在时间

单位时间产出极低的原因在 `evaluateBoard`（行 3625）：每个叶节点都要
- 全盘 361 格 × 4 方向 `lineInfo`（每条线起点才计分）；
- `comboBonus(color)`：扫描己方棋子邻域，每个候选点调 `countThreats` → 4×`lineInfo`，上限 128 次；
- `threatSpaceBonus(color)`：同样再扫一遍，上限 48 次（双方各一次）。

也就是说**一个叶节点 ≈ 上千次 `lineInfo`**。这是"预算花完只搜到 3 层"的直接原因。

## 三、AI 强度：根因清单（按影响排序）

### A1. 决策阶梯把搜索架空了（**最高优先级**）
`getBestMove` 的 ②~⑪ 是"先到先得"的短路返回：只要 `resolveThreats` 认为"我有个活三"，AI 就会直接下这个活三，**哪怕搜索会算出这一步会输**。阶梯的每一步都是单方面的（只看我/只看他），没有一步是全局最优比较。后果：
- 参数旋钮失效（证据 1、2）；
- 会为了做活三而放过更好的双威胁 / 会为了挡一个非致命点而放弃自己的必胜线路；
- 无法做到"更长的杀棋链"——因为 VCF/VCT 窗口只有 10 层且是独立搜索，不与主搜索共享信息。

### A2. 静态评估太粗糙（**第二优先级**）
- `PATTERN_TABLE`（行 3358）只有 **(连子数 × 开放端数)** 两个维度，`lineInfo` 只统计**连续同色子**，因此：
  - **不看空位结构**：`_XX_X_`（跳三）、`X_XXX`（跳四）这类棋型在"当前盘面"上被算成二/三，只在"落子那一手"才被临时识别；
  - 实测：白方连活三 `evaluateBoard = -46293`，白方跳活三 `X_XX` 只有 `-20658`（**差 2.2 倍**）——评估函数系统性低估跳型，导致 AI 在需要"补断点"的局面下算不出价值；
- 分档严重失真：`PATTERN_TABLE[3] = [1000, 1000, 10000]`（眠三=1000、活三=10000），`[4] = [10000, 10000, 100000]`（**冲四=10000 竟然和活三同分**）。而 `countThreats` 判定用的是 `s >= LIVE_THREE_SCORE(10000)`，于是**"眠三"在某些分值路径上会被当成威胁**、冲四与活三在组合判断里无法区分；
- 没有"两头封死的死棋型以外的**形状分档**"（活二/眠二/跳二/跳三/双二/双三/三四 的经典分级）；
- 评估是纯静态求和，没有"轮到谁"以外的深度修正，也没有"必胜/必败距离"。

### A3. 没有必胜距离（Mate distance）与胜负区分
`minimax` 命中必胜直接返回 `WIN_SCORE`（行 3787），无论 3 步后赢还是 20 步后赢都一样。导致：**该收的时候不收**（不优先最短杀），**该拖的时候不拖**（败局中不优先延长），也没有 `WIN_SCORE - depth` 这种"越早赢越好、越晚输越好"的标准写法。这是实测"平均 31 手、每局一模一样"的一个直接来源。

### A4. 评估与搜索的"攻防权重"是手调常数
`evaluateBoard` 里对方分 ×1.1、候选分 `attack + defend*0.8`、`DOUBLE_THREAT_BONUS=30000`、`TEMPO_BONUS=1500`、`WIN_RATE_SCALE=40000` 全是硬编码经验值，没有自对弈调参机制，也没有按棋型危险度的严格分级（活四 > 双冲四 > 冲四+活三 > 双活三 > 冲四 > 活三 的经典序）。

### A5. 搜索/剪枝质量不足
- `minimax` **每个节点**都调 `findImmediateWin`（含 `canWinNow` 全盘邻域扫描）与两次 `forcingMovesOf`，节点开销非常大；
- 叶节点评估极重（证据 4），有效深度上不去；
- 置换表用 **32 位 Zobrist**（碰撞率不低）且 `ttMap` 超 30 万条就 `clear()`（行 3758），会丢掉整局积累；
- `historyTable` 用 `Int32Array(361)` + 下标 `r*19+c` 硬编码 19（行 3819/3844/3865）——目前 13/15/19 都安全，但一旦支持 21 路就数组越界；
- 没有静止搜索（quiescence）、没有 null-move、没有 aspiration window、没有 PVS；
- `killerTable` 只按剩余深度索引（`killerTable[depth]`），没有按 ply/方向区分。

### A6. 开局库太薄
`OPENING_BOOK` 覆盖 0~8 子、生成器说 860 个规范化局面，但实测文件里**实际只有 29 个 key**，且 `bookMove` 只在盘面 ≤8 子且前面所有战术层都不命中时才会被用到。开局主要靠 `openingMove` 的"中心 9×9 + 距离加权 + 随机"——这是**没有战术内容的经验规则**，面对会下的人前 10 手就会落后。

### A7. 规则缺失影响强度定义
只支持"五连即胜、无禁手"。标准五子棋（尤其是黑方先手）依赖**禁手规则**（黑三三/四四/长连禁手）来平衡先手优势；没有禁手 + 先手必胜（证据 3）= 高难度对局体验"要么我赢要么 AI 赢，没法公平练棋"。另外没有"交换/指定开局"等平衡规则。

### A8. 主线程同步搜索会冻结 UI
`getBestMove` 是同步函数，困难档单步最长约 2.7s（perf 实测 2758ms），期间**页面完全卡死**（无 `requestAnimationFrame`、无 Worker、无进度提示）。教育模式的 `refreshHint()`（行 4287）在玩家每走一步后都会用 medium 档再算一次推荐点，等于**玩家每步要等两次思考**。

### 4.2 联机功能（服务端已经很强，前端补位）

- 没有**观战**、没有**悔棋协商**（前端直接禁用悔棋，行 1140）、没有**对局内聊天记录持久化**；
- 没有**重连后的比分/手数恢复**（快照里没有 moveHistory，所以重连后**无法悔棋也无法复盘**）；
- 房间没有**密码/私有开关**（5 位房号可被猜）；
- `handleMove` 的服务端校验很完整，但没有**落子频率与"恶意思考"上限**（限频 20 msg/s 只防刷消息）。

### 4.3 代码架构（这是"功能加不快"的真正原因）

1. **单文件巨石**：任何改动都要在 4688 行里找位置；CSS 与逻辑同文件；68KB 开局库以字面量形式内联在 JS 里（行 680），**每次改一行代码都要重新解析这份巨型 JSON**。
2. **没有模块边界**：AI 引擎、画布渲染、在线协议、QR 编码器全部共享 40+ 个全局 `let`。想单独复用 AI（比如做个 CLI 或服务端 AI）只能靠"正则从 HTML 里抠函数"这种办法——这正是 `work/*.js` 里 13 个脚本在做的事，脆弱且不能防回归。
3. **框架是空壳**：`GameAdapter` 声称支持多游戏，但 `games/*.js` 三个文件都是 `statusEl.textContent = '开发中'`；框架全局（`canvas`、`EMPTY/BLACK/WHITE`、`statusEl`）直接暴露给插件，多游戏并存会互相污染。
4. **测试方式不可持续**：`work/ai-threat-test.js`（72 断言）、`work/ai-scoring-test.js`（41 断言）覆盖面不错，但加载方式是把 HTML 当字符串 `extractFn`——重构一次就全废。
5. **仓库卫生**：根目录躺着 8 个一次性修复产物（`_damaged*.txt`、`_fixed.html`、`_fix1.json`、`_match-report.txt`、`_bad-summary.txt`、`_remaining-bad.txt`，合计 577KB），`work/` 里还有 `gomoku.html.damaged-backup`、`gen-part*.js`、`dump-*.js`、`fix-part2.js` 等十几个同类脚本，容易和真实产物混淆（`_fixed.html` 281KB 甚至比正主还大）。

## 五、界面：干净 / 简便 / 实用

### 5.1 当前界面的问题

**信息架构问题：**
- **模式按钮与工具按钮同级**：`双人对战 / 人机对战 / 在线对战 / 悔棋 / 重新开始` 五个按钮挤在 `#toolbar` 一行（行 302-308），模式是"上下文"，悔棋/重开是"动作"，语义不同却长得一样。
- **设置区 7 个控件常驻**：游戏、棋盘、AI 难度、教学点评、推荐点、开局猜先、胜率显示（行 309-331）全部一行 flex-wrap，与当前模式无关的控件只是**置灰**（行 1132-1139），视觉噪音大。
- **在线面板极长且默认占位**：`#onlinePanel`（行 332-424）含服务器地址、房间号、邀请链接、分享、扫码、房间大字、二维码、双方玩家卡、昵称、语音、视频、挂断、来电横幅、通话视频区、聊天开关、快捷语、聊天输入、状态、19 行使用说明——**这是一整屏的说明书**，而且是切到在线模式才显示，切换瞬间页面高度剧烈跳动。
- **胜率面板常驻**：`#winRatePanel`（行 429-432）即使双人模式不可用也占着版面。
- **`<h1>五子棋</h1>` 占了首屏**：标题对工具型页面没有价值。

**可用性问题（可验证）：**
- **高分屏模糊**：`resizeCanvas()`（行 966）只设 `canvas.width/height`，**没有 `devicePixelRatio` 缩放**（全文 `devicePixelRatio` 出现 0 次）。19 路画布逻辑尺寸 760×760，在 2x 屏上按 760 物理像素渲染 → 线条和棋子发虚。
- **移动端体验差**：全文没有 `touchstart`、没有 `matchMedia`、没有 resize 监听（各 0 次）。19 路棋盘固定 `CELL_SIZE=40` + `MARGIN=20` = 760px 宽，**在 375~430px 宽的手机上直接溢出**，只能靠浏览器缩放，而缩放后 `getBoundingClientRect` 的点击换算虽然仍成立，但交互精度很差。
- **每次全量重绘**：`draw()` 重画 361 条线 + 全部棋子（行 2489-2497）。教学模式下 `updateTeachBlink` 每 300ms 触发一次整盘重绘（行 2635），而每次重绘又调 `findImmediateWin(aiColor)` **做全盘扫描** —— 3.3 次/秒的无效全盘搜索。
- **无悬停预览、无落子动画、无音效**：落子即"啪"地出现，手感单薄。
- **无键盘操作**：`keydown` 只用了 2 处（聊天、昵称），`preventDefault` 0 次，方向键/回车无法下棋，**完全不可无障碍使用**。
- **状态信息分散**：回合在 `#status`，胜率在 `#winRatePanel`，点评在 `#commentPanel`，在线玩家在 `#onlinePlayers`，房间状态在 `#onlineStatus` —— 同一件事（现在什么局面）分散在 4~5 个位置。
- **`AI_DELAY = 250ms` 的假思考**（行 636）：AI 已经算完（困难档 2.7s）后还要再等 250ms，观感上"卡一下"，而真正的计算期反而没有任何提示。

### 5.2 界面改造建议（原则：上下文相关、单列、渐进披露）

1. **顶部收敛为一条状态栏**：`●黑方（你）回合 · 第 12 手 · 胜率 63%` + 右侧一行小按钮。把 `h1` 去掉或缩成小 logo。
2. **模式改为分段控件（segmented control）**置于棋盘上方，悔棋/重开/提示/认输放到棋盘**下方**（贴近手指）。
3. **设置收进抽屉（drawer）或折叠面板**，按模式显示相关项：双人模式只显示棋盘与猜先；人机模式才出现 AI 难度/教学/胜率；在线模式才出现服务器与房间。
4. **在线面板拆分**：默认只显示"创建房间 / 加入房间"两个大按钮 + 房间号输入；建房后用一个**可折叠的邀请卡片**（大字房间号 + 二维码 + 复制），把 19 行说明改成 3 步引导 + "?" 展开详情。
5. **响应式**：按 `min(容器宽, 视口高)` 动态算 `CELL_SIZE`，配合 `devicePixelRatio` 缩放；`<768px` 时棋盘铺满宽、控件改图标化、面板改底部抽屉。
6. **画布增强**：坐标标注、悬停预览、最后一手高亮环、落子淡入 120ms、胜利连线动画、音效。
7. **渲染优化**：棋盘网格画到离屏 canvas 缓存一次（只有 `boardSize` 变化才重画），棋子增量绘制；闪烁动画用 `requestAnimationFrame` + 只重绘变化层，且把 `findImmediateWin` 的结果缓存到落子时算一次。
8. **可访问性/键盘**：方向键移动光标 + 回车落子、`Space` 悔棋、`Esc` 取消；`aria-live` 播报回合与结果。

## 六、AI 强度提升路线（按性价比排序）

### 阶段 0：可测量的地基（**必须先做，1~2 天**）

没有量尺就不可能有强度。现在改一行 AI 代码，唯一能参考的是 `work/ai-threat-test.js` 这种单点断言。

1. **抽出引擎模块**：把 AI 部分（行 620-699 常量 + 2649-4113 引擎 + 少量工具）抽成 `outputs/engine/gomoku-ai.js`，用 IIFE 挂 `window.GomokuAI` 或 UMD 导出；HTML 里 `<script src>` 引入。开局库改成 `fetch('./opening-book.json')` 或独立 `<script>`，**从 HTML 里搬走 68KB**。

3. **建"必杀题库"回归**：把 VCF/VCT/双三/四三/防双三 等 100+ 个手工局面（含正确解）落盘为 `work/positions.json`，每次改动跑一遍**必须全过**。

### 阶段 2：结构性提升（**2~3 周，收益最大**）

1. **换成标准博弈搜索架构**：
   - **Negamax + Alpha-Beta + PVS + 迭代加深 + 时间管理 + Aspiration Window**；
   - **置换表用 64 位 Zobrist（分高低 32 位存储）**，按深度优先替换（保留深层条目，不要 `clear()` 全清）；
   - **Move ordering 完整化**：TT move → 必胜/必挡 → 双威胁 → VCF 强制手 → killer → history → 启发式；
   - **静态搜索（quiescence）**：叶节点只延展"冲四/活四/成五"这类强制手，解决"评估被对手的强制手骗"的问题。
2. **把 VCF/VCT 从"独立小搜索"升级为"威胁空间搜索（Threat Space Search）的组成部分"**：
   - VCF 用**增量式的冲四列表**（维护每个方向的四子窗口），而不是每层全盘 `vcfForcingMoves`；
   - VCT 加入"双威胁节点"和"对方有反杀"的剪枝（现在是纯 AND 节点，遇到对方反四会误判）；
   - 窗口从 10 层提到 20+ 层，节点上限 5 万级（有阶段 0 的 bench 兜底风险）。
3. **评估函数重写为标准棋型评分**：
   - 4 个方向 × 每个方向的**所有长度 5/6 窗口**（6 窗口用于识别活四/跳四）；
   - 棋型分类表（成五 / 活四 / 冲四 / 跳四 / 双冲四 / 活三 / 跳三 / 眠三 / 活二 / 跳二 / 眠二），**按双方棋型组合给局面分**（经典做法：己方棋型分 - 对方棋型分×权重，权重按"进攻方先手"调整）；
   - 加入**禁手检测面**（见阶段 3）后，黑方的三三/四四可被当作负分。
4. **自对弈调参**：用 bench 跑参数网格（各棋型权重、攻防系数、候选宽度、深度），用**胜率**而不是感觉挑参数。这一步通常能再多 100~200 Elo 的效果。
5. **服务端 AI（可选）**：同一份引擎在 Node 里跑，前端通过 WS 请求"AI 应手"，好处是：不冻结界面、能用满 CPU、手机上也能开困难档。实现成本低（引擎已是纯函数）。

### 阶段 3：规则与体验层（让"强"变得有意义）

1. **禁手规则（可选开关）**：黑方三三、四四、长连禁手；带禁手的评估会**主动做禁手陷阱**，这是五子棋 AI 的高阶能力，也是平衡先手的关键。
2. **开局规则**：指定开局 / 三手交换 / 五手两打（可选），让"先手必胜"不再成立。
3. **难度档重做**：现在是 easy/medium/hard 三档，但实测 hard 与 medium 的差别被阶梯掩盖。建议改成**用"搜索深度 + 是否允许犯错（按胜率分位随机）+ 思考时间"三维定义**，并新增"入门/新手"档（会漏防活三，但不会漏防冲四）。

### 阶段 4：把 AI 从主线程解放（体验刚需）

- 方案 A（最小改动）：`setTimeout` 分片搜索，每 30ms 让出主线程，UI 显示"思考中"。
- 方案 B（推荐）：引擎搬进 **Web Worker**（引擎已是纯 JS，把 `board` 传进去即可），主线程永不卡顿，还能顺便实现"后台思考（ponder）"。
- 方案 C：服务端 AI（阶段 2.5）。
